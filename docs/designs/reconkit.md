# Design: reconkit, a scope-safe recon CLI that grows into a pure-Python toolkit

Generated by /office-hours on 2026-11-26
Branch: main
Repo: reconkit (local, not yet on GitHub)
Status: APPROVED
Mode: Builder

## Problem Statement
Build an open-source recon CLI that takes a domain you are authorized to test and writes a clean report (report.md + report.json). It doubles as a GitHub portfolio piece. The user asked whether to build a pentest multitool instead. Decision: build reconkit first. Multitool-style features become later milestones, each implemented natively in Python behind the same scope gate.

## What Makes This Cool
- **It cannot touch what you did not authorize.** Scope is checked on every host: discovery results (only in-scope names are resolved; CNAME targets the OS resolver follows are not scope-checked in v1, but the final address must be public), the probe, and every redirect hop. Refused hosts are listed in the report, so the guarantee is visible.
- **One `pip install`, works on Windows.** No Go, no Docker, no external binaries. bbot's PyPI page lists Linux as a requirement (pypi.org/project/bbot); ProjectDiscovery's tools install as separate native binaries.
- **Later: "what changed on my domain?"** `--compare` turns a one-off scan into something you rerun every week.

## Constraints
- Windows 11, Python 3.15. Dependencies: httpx plus stdlib only (asyncio, socket, argparse, json, ssl).
- No external binaries (subfinder, httpx-cli, nmap), no Go, no Docker.
- v1 out of scope: port scanning, brute-forcing, directory fuzzing, vulnerability scanning, web UI, Docker, CI. Some of these return as opt-in milestones (see Roadmap). None enters v1.
- Done for v1 means: `pip install -e .` and `reconkit example.com --scope scope.txt -o out/` work end to end against a real authorized domain; one test covers the scope filter; the README has a pitch, install, usage, a sample report excerpt, and an authorized-use-only notice; MIT license.
- Don't create the GitHub repo or push until the user approves.

## Premises (agreed)
1. A menu-style pentest multitool that wraps binaries is the worse bet: it needs binaries this environment can't run, it's the most-cloned category on GitHub, and reviewers read it as low-effort.
2. reconkit won't beat bbot or subfinder on features. Its pitch: scope-safe by default, pure Python, Windows-native, one command gives a shareable report.
3. Scope enforcement is the headline feature. It fails closed (no scope file, an empty one, or a malformed one means exit with an error) and it is tested.
4. v1 distribution: `pip install git+https://github.com/<owner>/reconkit` after the user approves publishing. PyPI and CI are deferred.

## Cross-Model Perspective (Codex, gpt-6-astra, cold read)
- Coolest version: a repeatable inventory with evidence. Run it twice and see new hosts, changed tech, changed redirect destinations and scope refusals, with "unreachable this run" kept separate from "removed".
- Highest-severity point: "scope-safe" needs more than filtering the discovery results. Turn off httpx's automatic redirects and check each redirect hop against scope before following it. Test deceptive suffixes such as `example.com.evil.test`, and an in-scope host that redirects out of scope, using a mocked transport to prove the forbidden request is never sent.
- httpx supplies the plumbing. The interesting half is yours: scope semantics, crt.sh normalization, DNS, pacing (a connection limit is not a requests-per-second limit), fingerprint evidence, reporting.
- Its build order starts with the tested scope boundary.

## Approaches Considered
- **A: spec plus scope-safe redirects.** Your 6 features, with redirects checked per hop and refused hosts reported. Chosen as v1.
- **B: A plus fingerprint evidence plus `--compare`.** Chosen as v1.1.
- **C: menu-style multitool (rejected as a starting point).** It wraps binaries we can't install. Its useful capabilities return as native, scope-gated milestones below.

## Recommended Approach
Ship A as v1, then B as v1.1, then the toolkit milestones in order from least to most intrusive. Every module sends hosts through the same `in_scope()` gate, connects only to vetted IPs from the shared resolve step, and uses the same limiter for traffic to the target. Anything that sends traffic beyond plain recon also needs an explicit `--active` flag.

### Scope rules (v1, the security-critical logic)
- Each line of the scope file is either `example.com` (that exact host only) or `*.example.com` (any subdomain at any depth, e.g. `a.b.example.com`, never the apex). One `normalize()` (lowercase, strip trailing dot, IDNA) applies to scope lines, crt.sh names and redirect hosts. Blank lines and `#` comments are ignored; a file with no host lines left (missing, empty or comments-only) is a startup error. Any other line, such as a URL or an IP address, is a startup error.
- A host is matched on whole labels, never as a plain string suffix: `evil-example.com` and `example.com.evil.test` never match.
- The target domain itself must be in scope, or the tool refuses to start.
- Redirects: httpx's `follow_redirects=False`, with up to 5 hops followed by hand. Each hop's host is checked before the request goes out. An out-of-scope hop stops that chain and is recorded as `refused: out of scope`.
- **Non-public addresses are refused.** After resolving, a host whose addresses include any that are not public (`ipaddress.ip_address(a).is_global` is false: loopback, RFC 1918, link-local such as 169.254.169.254, reserved) is skipped and reported as `refused: non-public address`. To prevent DNS rebinding, the probe connects to the vetted IP itself (URL host = vetted IP, `Host` header = hostname, httpx `sni_hostname` request extension = hostname for TLS), so httpx never resolves the name again. Because httpx keys pooled connections on scheme, IP and port only, keep-alive is turned off (`httpx.Limits(max_keepalive_connections=0)`): every request opens a fresh connection with its own SNI, so a connection opened for one hostname is never reused for another on a shared CDN IP. At v1 request volumes the extra handshakes cost little. A redirect hop to a new host goes through the same path: scope check, resolve, public check, pin.
- **TLS:** first try https with certificate verification on. If verification fails, record `tls_error` (the `SSLCertVerificationError.verify_message`, e.g. "certificate has expired", "self-signed certificate") in report.json and as a column in report.md, then retry https once with verification off so the page is still captured. Plain http is tried only if the https connection fails (refused, reset or timeout), not on a TLS verification error or a non-2xx status. When both schemes are tried, both results are recorded.
- **Load limits (defaults, configurable):** `--concurrency 10` (one semaphore shared by DNS and HTTP), `--rate 5` (requests per second to target hosts, token bucket), `--timeout 10` (seconds per request). Redirect hops and the verification-off retry count against `--rate`; crt.sh does not. crt.sh: one unpaginated query, 60 s timeout, one retry after 5 s, then exit 3 with no partial report.
- The one test file `tests/test_scope.py` (stdlib unittest, no network) covers the 11 cases listed under Eng Review below: exact/wildcard-depth/apex, deceptive suffixes, normalization, malformed lines, missing/empty/comments-only files, out-of-scope target, non-public address refused, out-of-scope redirect never requested, relative Location resolved against the hostname.

## Open Questions
- Resolved in Eng Review: wildcard never covers the apex (R3-10); crt.sh failure behavior (R3-3).
- Resolved in v1.2: in-scope, non-wildcard SAN names that crt.sh didn't list get one extra probe round. Names found in that round's certificates are listed but not followed, so the run can't chain on.
- Resolved in v1.3: the DoH query uses `type=A`, not `type=CNAME`. One request returns the CNAME chain plus the NXDOMAIN status of its end, so dangling detection needs no second lookup. Every in-scope name is looked up, including ones the system resolver can't resolve, since those are exactly where dangling CNAMEs show up.
- Resolved in v1.1: a host missing from this run is reported at once as "Not seen this run", not as "Removed", with no state kept between runs. crt.sh is historical, so a missing name usually means crt.sh returned a partial answer, not that the host is gone. A host still listed but now failing shows up as a status change (e.g. ok → unreachable), so it stays separate from "not seen".

### R3-1 — feasibility (minor)

**Problem**

> Unchanged from R2-2. In httpx, certificate verification is set per client (AsyncClient(verify=...)), not per request, so the verification-off retry needs a second client or transport. The design still doesn't say so. The new keep-alive rule (httpx.Limits(max_keepalive_connections=0)) is described for the probe's client only. The verify=False client needs the same Limits, pinning and scope gate, and must count against the shared rate limiter.

**Remedy**

> Note that the retry uses a separate verify=False client built with the same Limits (keep-alive off), IP pinning, scope gate and the shared --rate/--concurrency limiter.

### R3-2 — feasibility (minor)

**Problem**

> Unchanged from R2-3. httpx does not raise ssl.SSLCertVerificationError directly. It raises httpx.ConnectError, with the ssl error chained as __cause__/__context__. Code that catches SSLCertVerificationError will never see it, so verification failures would be misread as connection failures, which then trigger the http fallback the design forbids for TLS errors.

**Remedy**

> Specify that tls_error is taken by walking the httpx exception's cause chain to the SSLCertVerificationError, and that this classification is what separates the TLS-error path from the connection-failure path.

### R3-3 — consistency (minor)

**Problem**

> Unchanged from R2-4. 'Single request' conflicts with the Open Questions behavior 'retry once, then exit'. A retry makes two requests: 2 x 60 s = up to 120 s before aborting. It is also unclear whether the crt.sh request counts against --rate.

**Remedy**

> Reword to 'one query (not paginated), 60 s timeout, retried once'. State the worst-case 120 s, and whether crt.sh counts against --rate.

### R3-4 — consistency (minor)

**Problem**

> Unchanged from R2-5. The Recommended Approach says every module uses 'the same rate limiter', but DNS lookups are now exempt from --rate. **Remedy**

> Reconcile the 'same rate limiter' sentence with the DNS exemption. State whether DNS and HTTP share one --concurrency semaphore, and whether DoH requests count against --rate.

### R3-5 — clarity (minor)
